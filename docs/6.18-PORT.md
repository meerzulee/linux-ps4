# Linux 6.18.44 Baikal port

Snapshot date: 2026-08-10

## Result

`6.18-baikal` is a patch-based port on the latest release in the Linux 6.18
LTS line at the snapshot date:

- base tag: `v6.18.44`
- peeled base commit: `1efe5d048a391de3ead2804b2e7f86376c356cc5`
- base repository: <https://github.com/gregkh/linux>
- local version: `-ps4-baikal`
- active patches: 54

The series applies with `git apply --check`; no fuzzy application is allowed.
The build procedure is pinned through the Debian container and produces a
kernel, config, System.map, stripped module archive, manifest, and checksums.
Older builds did not claim bit-for-bit reproducibility. The release target now
normalizes the kbuild timestamp, builder identity, build number, and module
archive metadata; a second clean build must still reproduce the release hashes
before publication.

The A39 artifact is now a **hardware-confirmed HDMI/XFCE candidate**, not yet a
release-stability claim. Keep the 5.4 recovery baseline until the remaining
gates below, including a second cold boot, pass.

## Build

OrbStack must be running and the Docker context must be `orbstack`:

```sh
./scripts/build-kernel-orbstack --target 6.18-baikal
```

The wrapper deliberately uses a named Docker volume for the kernel worktree.
Linux source contains names that collide on the default case-insensitive macOS
filesystem, so building directly in a bind-mounted source tree is unreliable.

Outputs land in `output/6.18-baikal/`. Verify them with:

```sh
cd output/6.18-baikal
sha256sum -c SHA256SUMS
cat manifest.txt
```

## What is in the release series

The active stack contains the platform boot path, PS4 southbridge/ICC support,
Liverpool/Gladius display path, Baikal AHCI and SDHCI IRQ/DMA handling, the
MT7668 vendor driver and its API ports, Aeolia-family xHCI handling, thermal
support, AMD IOMMU quirks, and narrowly gated PCI/MSI behavior. The Baikal
series now includes rmux's three-part MSI treatment as one unit: expose the
PS4 BPCIE IRQ domain as an MSI parent, program southbridge per-function MSI,
and retain the composer-default behavior required by that model. The three
patches are intentionally tested together; intermediate combinations are not
supported configurations.

The following were intentionally left out:

- bring-up-only display trace patches;
- experimental per-function MSI rewrites superseded by rmux's current model;
- the Baikal `sky2` experiment, because its own hardware work did not produce
  working TX and current rmux stable does not carry that false device model;
- the speculative UVD/VCE experiment chain;
- an older xHCI capability-retry experiment absent from current stable work.

The MT7668 subtree remains a large downstream vendor driver. It is included
because this repository has hardware evidence for it, but compilation warnings
and runtime behavior still require review before public release.

Hardware experiment A43 accepted A39 on the Baikal PS4. GoldHEN launched the
exact v25 ELF and Linux reported `6.18.44-ps4-baikal` build `#5`. On both the
initial bridge attach and the fbcon modeset, UART recorded successful lane,

systemd reached its graphical target, and the monitor displayed the XFCE GUI.
This confirms that the monolithic MN864729 command queue caused A38's black
screen and that restoring the v60-proven transaction boundaries fixes HDMI on
Linux 6.18.44. The exact A43 UART capture is linked from the omarchy-ps4
experiment ledger. A second unchanged cold boot and the remaining hardware
acceptance tests are still required before release.

Hardware experiment A51 repeated the unchanged A39 kernel after development
userspace provisioning. The bridge split stages passed again, `amdgpudrmfb`
initialized, LightDM reached the graphical target, and the `ps4` XFCE session
started. The internal MT7668 associated to its saved NetworkManager profile,
received a DHCP lease, and accepted pinned-key SSH. Remote checks found
`sshd`, NetworkManager, and LightDM active. This is a second HDMI/XFCE boot but
does not replace the pending true-cold-boot gate.

A51 also isolated the current boot delay from USB root handling: discovery
waited about 96 seconds while reads against the internal Toshiba SATA disk
timed out and produced buffer I/O errors. The external Kingston root then
resolved as `/dev/sda2`, mounted read-write, and completed startup in 1 minute
43.760 seconds. Treat internal SATA as degraded and diagnose it read-only;
do not mount or modify Sony partitions.

## Hardware acceptance gate

Use an unchanged, known-good XFCE userspace. Keep the 5.4 kernel and boot files
available for rollback. Record complete logs and test at least two cold boots.

1. Kernel reaches initramfs without faults or repeating interrupt errors.
2. USB root media enumerates consistently and mounts the intended filesystem.
3. HDMI reaches a stable 1080p60 console and XFCE session.
4. DRM initializes; `glxinfo` and a sustained OpenGL test work without reset.
5. SATA enumerates read-only. Do not mount or modify Sony partitions yet.
6. SDHCI and MT7668 probe; Wi-Fi associates and survives sustained traffic.
7. Bluetooth and DualShock 4 USB/Bluetooth reconnect behavior are recorded.
8. Fan, temperature, power button, shutdown, and reboot are safe.
9. External USB networking remains available as a recovery route.

Only after that gate should the same userspace be tested with a minimal Wayland
compositor, then bare Hyprland, and finally the Omarchy layers one at a time.
