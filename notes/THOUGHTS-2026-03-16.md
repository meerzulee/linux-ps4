## Session Goal
Port Linux 6.15 kernel to PS4 Slim (Baikal B1 southbridge) with UART serial debug.

- AMD Jaguar APU (8 cores, 1.594 GHz), x86_64
- 8GB GDDR5 unified memory (2GB mapped for Linux via kexec payload)

- 500GB Toshiba SATA HDD (internal)
- 128GB Kingston DataTraveler 3.0 USB (boot/rootfs)
- UART: Baikal southbridge hardware mod, CH340 USB-serial adapter
- UART MMIO address: 0xC890E000 (BAR2 0xC8800000 + offset 0x10E000)
- WiFi/BT: MediaTek MT7668 via SDIO

## Build Host
- macOS 26.3, Apple M5 ARM64, 24GB RAM
- Orbstack for Docker/Linux VM

## Key Discovery: Cross-compilation is BROKEN
Early attempts cross-compiled from ARM64 using `x86_64-linux-gnu-gcc`.
Both 5.4 and 6.15 kernels built this way triple-faulted on PS4.
The working 5.4 kernel the user had previously tested was a pre-built binary.

**Root cause**: Either VirtioFS corruption during kernel build (thousands of files
on macOS filesystem accessed via Orbstack mount) or subtle cross-compiler code
generation bugs for x86_64 boot code.

**Fix**: Build natively inside `--platform linux/amd64` Docker containers using
Rosetta 2 emulation. Slower (~15min vs 5min) but produces correct x86_64 binaries.

## Key Discovery: PS4 kexec payload incompatible with Linux 6.x
The PS4 kexec payload (`payload-1200-2gb-baikal.bin`) works with kernel 5.4
but causes immediate triple fault with kernel 6.15. This is because the 6.15
compressed kernel decompressor (arch/x86/boot/compressed/head_64.S) has 6 new
function calls that didn't exist in 5.4:
- `load_stage1_idt()` - loads interrupt descriptor table
- `configure_5level_paging()` - paging mode configuration
- `initialize_identity_maps()` - builds its own page tables

These new code paths are incompatible with the PS4 kexec payload's hardware
setup and identity mapping.

**Fix**: Two-stage kexec approach:
1. PS4 kexec payload → 5.4 kernel (compatible, boots successfully)
2. From within Linux 5.4, use Linux's own `kexec` to load 6.15
3. Linux's kexec properly handles modern boot protocols

## Key Discovery: earlycon causes triple fault after Linux kexec
The `earlycon=uart8250,mmio32,0xC890E000,115200n8` parameter causes 6.15 to
triple fault when loaded via Linux kexec (but works fine with 5.4 loaded via
PS4 kexec payload).

**Root cause**: Linux's kexec creates page tables that only map usable RAM
(per e820 map). The UART MMIO at 0xC890E000 (~3.2GB) is in PCI reserved space,
NOT in the identity mapping. The kernel's first earlycon printk writes to an
unmapped address → page fault → no IDT handler → double fault → triple fault.

The PS4 kexec payload maps the full 0-4GB range (4 PDPT entries × 1GB pages),
so earlycon works there. Linux's kexec is more selective.

**Fix**: Remove earlycon from 6.15 bootargs. UART output starts after PCI
enumeration when the BPCIE driver registers ttyS2.

## Key Discovery: APCIE UART is broken in 6.x
The crashniels 6.15 kernel has APCIE UART init commented out:
```c
// drivers/ps4/ps4-apcie.c line 537-538
// TODO (ps4patches): figure out why this dies a horrible and painful death.
//if ((ret = apcie_uart_init(sc)) < 0)
```
This means ttyS0/ttyS1 (APCIE) will never register. Only ttyS2/ttyS3 (BPCIE)
work. Must use `console=ttyS2,115200n8`.

## UART Address Discovery
Found from ps4-kexec source code: `#define BPCIE_BAR2 0xc8800000`
Confirmed by 5.4 kernel PCI enumeration:
```
pci 0000:00:14.4: reg 0x18: [mem 0xc8800000-0xc89fffff 64bit]
```
UART MMIO = BAR2 + BPCIE_RGN_UART_BASE = 0xC8800000 + 0x10E000 = 0xC890E000

- Baud: 115200, 8N1
- Linux device: ttyS2 (BPCIE UART, after APCIE registers ttyS0/ttyS1)

### Boot Flow (Two-Stage Kexec)
```
PS4 firmware (Orbis OS / FreeBSD 11)
  → GoldHEN exploit + payload-1200-2gb-baikal.bin
  → sys_kexec: loads 5.4 bzImage + initramfs from FAT32
  → PS4 kexec payload: fixes ACPI, quiesces CPUs, resets GPU
  → jumps to 5.4 compressed startup_64

Linux 5.4 (stage-1 bootloader)
  → boots with earlycon + keep_bootcon (UART output)
  → stage-1 init: mounts FAT32, finds 6.15 kernel
  → kexec -l bzImage-6.15 --initrd=initramfs-6.15.cpio.gz
  → kexec -e: Linux kexec with proper boot protocol

Linux 6.15 (target kernel)
  → boots silently (no earlycon - PCI MMIO unmapped)
  → PCI enumeration → BPCIE driver → ttyS2 registered → UART output
  → GPU init → framebuffer → HDMI output
  → mounts rootfs (/dev/sda3 ext4)
  → switch_root to Arch Linux systemd
```

## Root Cause Analysis - Why 6.15 Crashes

### What we've eliminated:
1. Cross-compilation bugs → built natively in x86_64 Docker ✓
2. earlycon MMIO access to unmapped PCI space → removed earlycon ✓
3. hardware_subarch = 0 (PC) → patched to 5 (PS4) ✓
4. CPU mitigations complexity → all disabled ✓
5. kexec payload incompatibility → using Linux's own kexec from 5.4 ✓
6. Wrong serial port → using ttyS2 (BPCIE) ✓

### What's left - the compressed decompressor:
The 6.15 kernel's compressed boot code (arch/x86/boot/compressed/head_64.S)
has 6 new function calls that didn't exist in 5.4:

```
5.4 compressed startup_64:          6.15 compressed startup_64:
  Calculate addresses                  Calculate addresses
  Set up stack                         Set up stack
  Decompress                           Load GDT
  Jump to kernel                       call load_stage1_idt        ← NEW
                                       call configure_5level_paging ← NEW
                                       Copy to relocation target
                                       Jump to relocated code
                                       Clear BSS
                                       call load_stage2_idt        ← NEW
                                       call initialize_identity_maps ← NEW
                                       call extract_kernel
                                       Jump to kernel
```

The critical difference: `initialize_identity_maps()` builds its OWN page
tables and loads them into CR3. In 5.4, the decompressor uses whatever page
tables the kexec purgatory provides. In 6.15, it replaces them.

If `initialize_identity_maps()` creates incorrect page tables (e.g., doesn't
map the memory where the decompressor's stack or code is), the next memory
access faults → no IDT handler → double fault → triple fault → instant reboot.

### Theory: The kexec purgatory's page tables work for 5.4 but 6.15 replaces them with broken ones

The kexec purgatory maps enough memory for the kernel to start. But 6.15's
`initialize_identity_maps()` builds minimal maps that only cover:
- _head to _end (compressed kernel)
- boot_params
- command line

If the stack, relocation target, or initramfs is outside these ranges, the
new page tables would unmap memory that was previously accessible → crash.

## Next Steps - Three Ideas

### IDEA 1: Load vmlinux (uncompressed ELF) via kexec [RECOMMENDED - TRY FIRST]
**Rationale**: Completely bypasses the compressed decompressor (head_64.S)
which is where all the new 6.x code that causes the crash lives.

kexec supports loading ELF files directly:
```bash
kexec -l /mnt/boot/vmlinux-6.15 --initrd=... --command-line="..."
kexec -e
```

This jumps directly to the decompressed kernel's startup_64, skipping ALL
of the compressed boot code (load_stage1_idt, configure_5level_paging,
initialize_identity_maps, extract_kernel).

**If vmlinux boots**: The crash is confirmed to be in the decompressor.
We can then focus on fixing just the decompressor for PS4.

**If vmlinux also crashes**: The problem is in the kernel itself, not
the decompressor. Need to investigate further.

**Size**: vmlinux is 435MB (debug), 34MB stripped. Fits on FAT32.

**Steps**:
1. Build 6.15 natively in Docker, extract stripped vmlinux
2. Patch hardware_subarch in vmlinux ELF (different offset than bzImage)
3. Copy to USB FAT32
4. Boot 5.4, mount USB, kexec with vmlinux
5. Observe UART/HDMI output

### IDEA 2: Try Linux 6.1 LTS instead of 6.15
**Rationale**: 6.1 is the current LTS. Its compressed decompressor is
simpler than 6.15. The `initialize_identity_maps` exists but is less
complex. Port crashniels PS4 patches to 6.1 and test.

**Pros**: Simpler decompressor, longer support lifecycle
**Cons**: Need to port PS4 patches (may require significant work)

### IDEA 3: Patch the 6.15 decompressor for PS4
**Rationale**: Add PS4-specific code to `initialize_identity_maps()` that
creates a full 0-4GB identity mapping (like the PS4 kexec payload does)
instead of the fine-grained per-region mapping.

**Pros**: Fixes the root cause
**Cons**: Requires kernel source modification, understanding of x86 page tables

### IDEA 4: Use root=LABEL instead of root=/dev/sdaN
**Lower priority but important**: The USB device ordering is not deterministic
(sometimes sda, sometimes sdb). Change bootargs to use filesystem labels:
```
root=LABEL=psxitarch rootfstype=ext4
```
This works regardless of device enumeration order.
